第一层 · 声音在电脑里是什么
============================================================

  【声卡只认一串数字】

  喇叭发声靠膜片振动。膜片往前推空气，你听到声音。
  声卡收到的就是一串数字，每个数字代表某个瞬间膜片应该在什么位置：

    [0, 152, 301, 428, 380, 210, -50, -280, ...]

  一秒给它 44100 个这样的数字，膜片按这个轨迹振动 44100 次。
  这串数字叫 PCM 数据。

  ffmpeg 命令里那几个参数就是在描述这串数字：

    -ar 44100    一秒 44100 个数字（采样率）
    -ac 2        左右两个声道，各一串
    16 位        每个数字用 16 个二进制位，范围 -32768 ~ 32767

  ★ 为什么是 44100
    人耳听得到的最高频率约 20000 Hz，
    采样率要超过它的两倍才能完整记录（奈奎斯特定理）。
    44100 是 CD 定的标准，一直沿用。

  【wav 就是 PCM 加个帽子】

    [44 字节文件头]  写着"双声道、44100、16 位"
    [PCM 数据    ]  就是那串数字，一直到文件结束

    几乎不用解码。读出来直接扔给声卡。

    这也是 wav 那么大的原因 —— 一分钟约 10 MB，完全没压缩。
    项目 14 首共 438 MB。

  【mp3 不一样】

    mp3 把"人耳听不出差别"的信息扔掉了，一分钟只要 1 MB。
    代价是播放前必须先解码成 PCM。
    解码靠系统装的解码器，不同电脑可能不一样。

    ★ 这就是 PlaySound 不支持 mp3 的原因 ——
      它太简单了，只会读 wav 头然后把数据推给声卡，不会解码。

第二层 · 你的程序在哪个位置
============================================================

    你的程序
       ↓
    PlaySound  ← 最简单，项目用这层
       ↓
    MCI / DirectSound / WASAPI  ← 越往下越强，代码越多
       ↓
    音频驱动
       ↓
    声卡

  你不可能直接跟声卡说话 —— 那是驱动的事。

  【为什么最后选 PlaySound】

  先看需求：
    - 背景音乐，同时只放一首
    - 每首无限循环
    - 场景切换时能换歌
    - 不需要音量控制、淡入淡出、BGM+音效同时响

  再看四个选项：

  ┌──────────────────┬────────────────────────────────────┐
  │ PlaySound        │ 只能 wav、只能一首                 │
  │                  │ 但你只需要一首，循环原生支持       │
  │                  │ 8 行代码  ★采用                    │
  ├──────────────────┼────────────────────────────────────┤
  │ MCI              │ 能放 mp3、查进度、调音量           │
  │                  │ 但 wav 不支持 repeat，循环要自己轮询│
  ├──────────────────┼────────────────────────────────────┤
  │ DirectSound      │ 能力强，代码量 10 倍               │
  ├──────────────────┼────────────────────────────────────┤
  │ SDL_mixer / FMOD │ 要装第三方库，交作业麻烦           │
  └──────────────────┴────────────────────────────────────┘

  ★ PlaySound 的"限制"正好是你的"不需要"。
    功能多的 API 不等于更合适的 API。

第三层 · PlaySound 怎么用
============================================================

  【函数原型】

    BOOL PlaySoundA(
        LPCSTR pszSound,   // 文件路径
        HMODULE hmod,      // 资源模块，用文件时传 NULL
        DWORD fdwSound     // 标志位
    );

    返回 TRUE(1) 成功，FALSE(0) 失败。

  【三个标志】

    PlaySoundA(file, NULL, SND_FILENAME | SND_ASYNC | SND_LOOP);

    SND_FILENAME   第一个参数是文件路径，不是资源名
    SND_ASYNC      异步 —— 立刻返回，不等播完
    SND_LOOP       循环 —— 放完自动从头再放

  【SND_ASYNC 是命根子】

    不加它，PlaySound 会一直阻塞到播完才返回。

    title.wav 是 3 分 50 秒，不加的话：

      play_bgm("bgm/title.wav");   // 卡在这里 230 秒
      begin_title();               // 3 分 50 秒后才执行

    整个游戏死在那一行。

    加了 SND_ASYNC，播放交给系统的音频线程，主线程立刻往下走。

  【SND_LOOP 必须配 SND_ASYNC】

    想想为什么 —— 循环是无限的，同步执行永远不会返回。
    所以 SND_LOOP 单独用没意义，
    微软文档里也明确写了必须配 SND_ASYNC。

  【| 是什么 —— 位标志】

    三个常量的实际值：

      SND_ASYNC    = 0x0001    二进制 0000 0001
      SND_LOOP     = 0x0008    二进制 0000 1000
      SND_FILENAME = 0x20000   二进制 ...0010 0000 0000 0000 0000

    每个占一个不同的二进制位。| （按位或）把它们合成一个数：

      0000 0001
      0000 1000
      ...0010 0000 0000 0000 0000
      ─────────── 或运算 ──────────
      ...0010 0000 0000 0000 1001

    PlaySound 内部再一位一位检查：
      "第 0 位是 1 吗？→ 异步"
      "第 3 位是 1 吗？→ 循环"

    ★ 这叫位标志（bit flag），Windows API 到处在用。
      以后看到一堆 A | B | C 的常量都是这个套路。

  【停止播放】

    PlaySoundA(NULL, NULL, 0);

    第一个参数传 NULL 表示"停掉当前正在放的"。

  【一个重要特性】

    ★ PlaySound 只能同时放一个。放新的会自动停掉旧的。
      所以 play_bgm 里不需要先手动停，直接放新的就行。

第四层 · 逐行拆代码
============================================================

  char now_bgm[100] = "";

    全局变量，记住"现在正在放哪一首"。
    = "" 让它初始为空串（第 0 个字符是 '\0'）。
    100 字节够用 —— 最长路径 bgm/ch5_planetarium.wav 是 23 个字符。

  ─────────────────────────────────────────

  void play_bgm(const char *file) {

    参数为什么是 const char* ——

      play_bgm("bgm/title.wav");     // 字面量的类型是 const char[14]
      play_bgm(bgm_chapter[3]);      // 数组元素也是 const char*

    写成 char* file 这两个调用都编译不过（见 bug 21）。

  ─────────────────────────────────────────

      if (strcmp(now_bgm, file) == 0) {
          return;
      }

    ★★★ 这三行是整个函数存在的理由 ★★★

    strcmp 比较两个字符串，相同返回 0。
    所以：要放的和正在放的是同一首 → 什么都不做，滚回去。

    【为什么必须有】

    看 main：

      while (1) {
          draw_memory_secene();
          while (!_kbhit()) { ... }
          char c = _getch();
          // 各种分支，可能调 play_bgm
      }

    玩家每按一个键，while(1) 转一圈。

    没有这三行，玩家在大厅走路：
      按 W → PlaySound(hall.wav) → 音乐从 0 秒开始
      按 A → PlaySound(hall.wav) → 又从 0 秒
      按 S → PlaySound(hall.wav) → 又从 0 秒
      按 D → PlaySound(hall.wav) → 又从 0 秒

      → 音乐永远播不过第一秒
      → 听起来是咔咔咔的杂音，不是音乐

    有了这三行：
      第 1 次 → now_bgm 是 ""，不等 → 真的播放 → 记下名字
      之后    → now_bgm 相等 → return → 音乐一点没受打扰
      换章节  → 参数变了，不等 → 真的换歌

    ★ 这不是优化，少了它系统就是坏的。

  ─────────────────────────────────────────

      if (PlaySoundA(file, NULL, SND_FILENAME | SND_ASYNC | SND_LOOP) == FALSE) {
          memset(now_bgm, 0, sizeof(now_bgm));
          return;
      }

    播放；失败就静默退出。
    失败原因：文件不存在、路径错、不是 wav、文件损坏。

    【memset 是干什么】

      memset(now_bgm, 0, sizeof(now_bgm));

      把 now_bgm 这 100 个字节全部填 0，等于清空成空串。
      （也可以只写 now_bgm[0] = '\0'; 效果一样 ——
        C 字符串只看到第一个 '\0' 就停。memset 更彻底。）

    【为什么必须清空】

      play_bgm("bgm/ch1.wav") 失败了
        如果不清空 → now_bgm 还是上一首 "bgm/hall.wav"
        但 PlaySound 已经把 hall.wav 停掉了（放新的会停旧的）

      再调 play_bgm("bgm/hall.wav")
        strcmp 相等 → return
        → 以为在放，实际早停了
        → 一点声音没有，而且永远放不回来

      清空之后，下次任何调用都会真的执行。

    【为什么不打印错误】

      要"缺一首歌不影响玩游戏"。
      如果这里 printf，那行字会打在游戏画面上，破坏排版。

      而且这让你能先写代码、后补音乐 ——
      文件没准备好时游戏照样跑，只是没声。

  ─────────────────────────────────────────

      strcpy(now_bgm, file);
  }

    播放成功了，把名字记下来。
    下次调用时开头那个 strcmp 才有东西可比。

    【顺序为什么不能反】

      必须先播放，成功了再记。

      反过来的话：
        strcpy(now_bgm, "bgm/ch1.wav");   // 先记
        PlaySoundA(...)                    // 失败了
        // 之后 play_bgm("bgm/ch1.wav") → strcmp 相等 → return
        // → 永远不重试，永远没声

      现在的顺序保证：
      ★ now_bgm 里的名字，一定是真的在放的那一首。

  ─────────────────────────────────────────

  void stop_bgm() {
      PlaySoundA(NULL, NULL, 0);
      memset(now_bgm, 0, sizeof(now_bgm));
  }

    两行：停掉播放，清空记录。

    第二行必须写，否则：
      stop_bgm() 停了，但 now_bgm 还是 "bgm/hall.wav"
      play_bgm("bgm/hall.wav") → strcmp 相等 → return
      → 以为在放，实际早停了 → 没声音

第五层 · #pragma comment(lib, ...) 是什么
============================================================

    #pragma comment(lib, "winmm.lib")

  【编译分两步】

  第一步 · 编译：源.cpp → 源.obj
    只检查语法。看到 PlaySoundA(...)，编译器去头文件里查
    "有这个函数吗？参数对得上吗？" 对得上就放行。
    ★ 它不需要知道这个函数的代码在哪。

  第二步 · 链接：源.obj + 各种库 → Project2.exe
    这一步要真的找到 PlaySoundA 的机器码。

    PlaySoundA 的实现在 winmm.dll 里（Windows 装好就有）。
    链接器需要一个"索引文件"告诉它去哪找 —— 那就是 winmm.lib。

  不加这行的话，编译能过，链接会报：
    error LNK2019: 无法解析的外部符号 PlaySoundA
  意思是"我知道你要调这个函数，但我找不到它在哪"。

  【为什么用 #pragma 而不改项目属性】

  两种加法都行：
    ① 右键项目 → 属性 → 链接器 → 输入 → 附加依赖项 → winmm.lib
    ② #pragma comment(lib, "winmm.lib")

  ★ 项目属性存在 .vcxproj 里，换台电脑、重建项目就丢了。
    #pragma 写在源码里，跟着代码走。
    交作业时老师直接编译就能过。

  #pragma 是编译器扩展，只有 MSVC 认。
  但你只在 Windows 上跑，无所谓。

第六层 · bgm_chapter[7] 为什么这样设计
============================================================

  const char* bgm_chapter[7] = {
      "bgm/hall.wav",              // [0] 回廊之厅
      "bgm/ch0.wav",               // [1] prologue.txt    · 序幕 深夜
      "bgm/ch1.wav",               // [2] library.txt     · 第一章 初遇
      "bgm/ch2.wav",               // [3] rooftop.txt     · 第二章 相伴
      "bgm/ch3.wav",               // [4] hospital.txt    · 第三章 裂缝
      "bgm/ch4.wav",               // [5] planetarium.txt · 第四章 缺席
      "bgm/ch5_planetarium.wav"    // [6] finale.txt      · 第五章 回响
  };

  【为什么开 7 个】

  因为 cur_chapter 是这么用的：
    0     = 大厅
    1 ~ 6 = 六章

  开 7 个、[0] 给大厅，cur_chapter 可以直接当下标，不需要加减：

    play_bgm(bgm_chapter[chapter]);    // chapter 是 1~6，直接用
    play_bgm(bgm_chapter[0]);          // 大厅

  只开 6 个的话，得写 bgm_chapter[chapter - 1]，
  而且大厅的音乐还得另外单独写一行。

  ★ 多一个 -1 就多一个出错的机会。
    项目里 difsecene[chapter - 1] 就是这种写法，
    每次用都得停下来想"要不要减 1"。

  【项目里所有这类数组都是 7 个】

    int pangbai_alredy[7];
    int game_begin_locked[7];
    const char* the_chapter_Walls[7];
    every_secene_color chaptercolors[7][12];
    mujian_zhuanhuan chapter_zhuanhuan[7];
    const char* bgm_chapter[7];      // ← 跟它们对齐

  下标含义完全一致。以后看代码时看到 [3] 就知道是第三章。

  【文件名为什么和下标错一位】

    你的文件      游戏显示        场景文件          cur_chapter
    ─────────    ──────────      ─────────────    ───────────
    ch0          序幕 深夜        prologue.txt          1
    ch1          第一章 初遇      library.txt           2
    ch2          第二章 相伴      rooftop.txt           3
    ch3          第三章 裂缝      hospital.txt          4
    ch4          第四章 缺席      planetarium.txt       5
    ch5          第五章 回响      finale.txt            6

  你的编号和游戏显示是一致的（都从"0 / 序幕"开始），
  只有代码内部的 cur_chapter 多 1。

  ★ 数组存在的价值就是"只错一次"。
    错位关系写在数组里，调用处永远写 bgm_chapter[chapter]。

    不用数组的话就得写六个 if-else，每个都要正确处理错位。
    而且那段代码在 get_to_the_secene 里出现两次（首次进/重玩），
    等于十二次机会出错。

第七层 · 路径
============================================================

  【"bgm/hall.wav" 是相对路径】

    bgm/ 表示"当前工作目录下的 bgm 文件夹"

    三种写法：
      "bgm/hall.wav"              相对路径 + 文件夹   ← 用这个
      "hall.wav"                  相对路径，wav 和 exe 同层
      "E:/.../bgm/hall.wav"       绝对路径，换电脑就失效

    ★ 用文件夹不是技术要求，纯粹是为了组织文件 ——
      14 个 wav 有 438 MB，和 7 个 txt 混在一层会很乱。

  【斜杠用 / 不用 \】

    Windows 习惯用 \，但代码里写 \ 要转义：

      "bgm\\hall.wav"     // 两个反斜杠才代表一个
      "bgm/hall.wav"      // 干净

    Windows API 两种都认（PlaySound、fopen、CreateFile 全都认），
    所以一律用 /。

  【工作目录不是 exe 所在目录】

    相对路径是从【工作目录】算起的，不是从 exe 位置算起的。

    实测这个项目在 VS 调试时工作目录是：
      E:\xingzhihueixiangDaima\Project2\Debug

    而双击 exe 时工作目录是 exe 所在目录。
    这两个可能不一样，所以 bgm/ 复制到了五个位置。

    ★ 这也是那 7 个 txt 在好几个目录都有一份的原因 —— 同一个道理。

  【1】标题曲 —— 顺序不能反

        system("cls");
        if (pangbai_alredy[0] == 0) {
            play_bgm("bgm/titile-hall.wav");
        }
        play_the_pangbai(0);
        play_bgm(bgm_chapter[0]);

          if (pangbai_alredy[idx] == 1) { pop_stack_time(); return; }  // 只播一次

    加了守卫：第二次跳过序幕曲，直接进大厅曲，干净。

    ★ 注意 play_bgm(bgm_chapter[0]) 在守卫外面，每次都执行
      —— 满足"每次返回或进入 hall 都播放"。

      章节卡是一道幕布，音乐在幕布升起时才进来。
      跟卡片同时起会把卡片的庄重感冲掉。

    重玩 —— if 整块被跳过，else 里必须补一次，
      否则会一直放着大厅的曲子。★ 最容易漏的一处。

第九层 · 为什么 Sleep 不影响音乐
============================================================

  代码里到处是 Sleep(200)、Sleep(3000)、while (_getch() != ' ')。

  ★ 音乐完全不受影响。

  因为 SND_ASYNC 让播放跑在【系统的音频线程】里。
  你的主线程睡多久、阻塞多久，都跟它无关。

  SND_LOOP 的循环逻辑【也在系统那边】——
  "放完自动从头再放"不需要你的代码参与。

  这就是为什么"每首都循环、不用管时间"一个标志就解决了。

  ★ 反过来说：如果不加 SND_ASYNC，
    PlaySound 会阻塞到播完 ——
    游戏会卡死在 play_bgm 那一行 3 分 50 秒。

============================================================
第十层 · 那个 259 是怎么回事
============================================================

  这部分是我讲错的地方，值得单独说，
  因为【排查方法比结论更有用】。

  【原本用的是 MCI】

    mciSendStringA("open \"bgm/title.wav\" alias bgm", NULL, 0, NULL);
    mciSendStringA("play bgm repeat", NULL, 0, NULL);

    我以为 repeat 就是循环。
    文档里确实写着 repeat 是 play 命令的参数。

  【但它对 wav 无效】

    MCI 有多种"设备类型"：

      waveaudio   放 wav    ★不支持 repeat
      sequencer   放 MIDI    支持 repeat
      cdaudio     放 CD      不支持 repeat

    repeat 只对 MIDI 序列器有效。

    我看了命令表，但没看【设备类型的支持矩阵】。

  【后果：整条命令失败】

    不是"忽略 repeat 但照样播放"，
    而是整条 play 命令被拒绝：

      play  返回 259 : 驱动程序无法识别指定的命令参数。
      状态 = stopped

    一声都没有。

  【诊断代码是怎么定位的】

    输出：
      工作目录 = E:\xingzhihueixiangDaima\Project2\Debug
      [1] fopen 成功
      [2] open  返回 0   : 指定的命令已被执行。
      [3] play  返回 259 : 驱动程序无法识别指定的命令参数。
      [4] 状态 = stopped
      [5] 长度 = 230528 毫秒

    这六行的信息量：
      [1] 排除了"路径错"
      [2] 排除了"文件打不开"
      [5] 读到了 230528 毫秒 → 排除了"格式不对""文件损坏"
      [3] 锁定：就是 play 这一步失败的
      [4] 确认：确实没在播

    ★ [5] 那一行是关键。
      能读出正确长度说明文件被完整解析了，
      问题只可能在 play 命令本身。

  【mciGetErrorStringA 是最有用的工具】

    259 这个数字本身什么都看不出来。

      mciGetErrorStringA(259, msg, 300);
      // msg = "驱动程序无法识别指定的命令参数。"

    "命令参数" —— 一句话指向 repeat。

  【三条教训】

    ① 返回值一定要检查，而且要翻译成人话
       原来的 play_bgm 里检查了 open 的返回值，
       但没检查 play 的。两个都检查的话第一次运行就能发现。

    ② 分步诊断比通读代码有效
       代码看起来完全正确 —— 它真的没有语法错、没有逻辑错。
       ★ 错的是对 API 行为的假设。
         假设是查不出来的，只能打印实际返回值。

    ③ 多打几个 status，缩小范围最快
       length 那一行值一千行代码 —— 它一下排除了三种可能。

  ┌────────────────────────────┬──────────────────────────────────┐
  │ PCM                        │ 一串数字，每个代表膜片位置       │
  │ wav                        │ 44 字节头 + PCM，几乎不用解码    │
  │ mp3                        │ 压缩过要解码，PlaySound 不认     │
  │ PlaySound                  │ 只放 wav、只放一首               │
  │                            │ —— 但你只需要一首                │
  │ SND_ASYNC                  │ 异步，★不加会卡死                │
  │ SND_LOOP                   │ 循环，必须配 SND_ASYNC           │
  │ |                          │ 位标志，多个常量合成一个数       │
  │ now_bgm                    │ 记住现在放哪首                   │
  │                            │ ★没它音乐永远停在开头            │
  │ strcmp == 0 就 return      │ ★整个函数存在的理由              │
  │ 先 PlaySound 再 strcpy     │ 顺序不能反                       │
  │ stop_bgm 要清 now_bgm      │ 否则下次 play_bgm 会误判         │
  │ #pragma comment(lib,...)   │ 告诉链接器去哪找 PlaySoundA      │
  │ bgm_chapter[7]             │ [0] 给大厅，cur_chapter 直接当下标│
  │ "bgm/xxx.wav"              │ 相对路径，从工作目录算起         │
  │ play_bgm 在 begin_title 前 │ ★阻塞函数是一道墙                │
  │                            │ 要在它"期间"生效就写在它前面     │
  │ MCI 的 repeat              │ 只对 MIDI 有效，对 wav 返回 259  │
  └────────────────────────────┴──────────────────────────────────┘
