============================================================
《星空回响》学习笔记 13 · 显示层与数据层必须同步
============================================================

【学习时间】2026-07-24

【本笔记内容】
- 一个"D 走过去就没了"bug 的完整调试记录
- 什么是"显示层"，什么是"数据层"
- 为什么两层必须同步
- 类似 bug 的通用防御思路


============================================================
【一、bug 现象】
============================================================

hall.txt 里画了两行 D：

  y=6:  =    D       D       D       D       D       D  =
  y=9:  =    D       D       D       D       D       D  =

代码里 difsecene[] 只在 y=6 那行画 6 个"真门"D：

  doors difsecene[6] = {
      {  5, 6, "prologue.txt"    },
      { 13, 6, "library.txt"     },
      ...
  };

  void draw_the_beginning_room() {
      for (int i = 0; i < 6; i++) {
          gotoxy(difsecene[i].x, difsecene[i].y);   // 在 y=6 画 D
          printf("D");
      }
  }

运行时：玩家走到 y=9 那行 D 附近，D 就没了。


============================================================
【二、问题分析】
============================================================

先问自己：屏幕上的字符，是从哪儿来的？

有两个来源：

  ① load_secene() 把 .txt 内容整行 printf 到屏幕上
  ② draw_the_beginning_room() 用 gotoxy 一个个 printf 到屏幕上

再问：屏幕上的字符，在内存里的 bg[][] 数组里有没有对应？

  ① load_secene() 打的字符 → bg[][] 里也存了
  ② gotoxy 单独画的字符 → bg[][] 里未必有

这就是"显示层"和"数据层"的区别：

  显示层 = 屏幕上你能看到的字符
  数据层 = 内存里 bg[y][x] 存的字符


============================================================
【三、擦除逻辑依赖数据层】
============================================================

主循环里玩家移动的擦除代码：

  gotoxy(px, py);                        // 老位置
  if (bg[py][px] == 'A' || 'B') { 恢复 A/B }
  else if (bg[py][px] != '\0') {
      setColor(15);
      printf("%c", bg[py][px]);          // 用 bg 里存的字符恢复
  }
  else {
      printf(" ");                       // bg 是 '\0' → 打空格
  }

关键：擦除永远只查 bg[py][px]，不管屏幕上实际显示的是什么。


============================================================
【四、bug 是怎么触发的】
============================================================

代码 draw_the_beginning_room() 在 (5, 6) 画了一个金色 D。
但 hall.txt 里 y=6 那行原本是空格（用户测试时的临时 .txt）。
所以：

  屏幕上 (5, 6) 显示 D    ← 显示层
  bg[6][5] = ' '           ← 数据层

玩家从 (5, 7) 向上走时挡不住（D 是墙，挡在 (5, 6)），
但是走到 (6, 6) 时 —— 会不会盖到 D？

  checkwall('D')=1 → 玩家挡不住走到 D 上
  但玩家的 @ 显示是靠"每步先擦老位置再画新位置"

只要有任何一次重画覆盖了 (5, 6)，
擦除逻辑查 bg[6][5] = ' '，就会把 D 擦成空格。

甚至更简单：进 hall 时 draw_the_beginning_room 之前，
load_secene 用 printf("%s", bg[i]) 把 y=6 那行整行打出来，
把 (5, 6) 打成了空格。然后 draw_the_beginning_room 再在
(5, 6) 补上金色 D。看似正常。

但 y=9 那行 D 呢？
load_secene 把它打出来了（bg[9][5]='D'，屏幕也显示 D），
可代码从不再重画 y=9 的 D，也没人保护它 —— 一旦玩家
移动路径经过附近，某个偶然的重画就把它盖掉了，
擦除逻辑查到 bg 是啥就恢复啥。


============================================================
【五、fix】
============================================================

把 difsecene[] 的 y 从 6 改成 9：

  doors difsecene[6] = {
      {  5, 9, ... },
      { 13, 9, ... },
      ...
  };

这样：

  hall.txt 里 y=9 有 D    → bg[9][x] = 'D'
  代码在 y=9 重画彩色 D    → 显示层也是 D

显示层 = 数据层 = 'D'
再怎么擦除、重画，都恢复成 D，不会消失。


============================================================
【六、通用防御思路】
============================================================

★ 铁律：凡是代码用 gotoxy 单独画的字符，
        必须保证 bg[y][x] 里存的是同一个字符。

三种做法：

  做法 1（推荐）：让 .txt 里也写上这个字符
                 数据层自然同步，代码只改颜色不改字符

  做法 2：每帧都重画一次
         不依赖擦除逻辑恢复，主循环末尾调用一次 draw_XXX

  做法 3：手动同步 bg
         代码画 D 之后紧接着 bg[y][x] = 'D'
         (不推荐，容易漏)

hall 用的是做法 1：
  hall.txt 里 y=9 有 D          → bg[9][x]='D'
  draw_the_beginning_room 也在 y=9 画彩色 D
  两层字符相同，只是颜色不同


============================================================
【七、这类 bug 的判断口诀】
============================================================

看到"XX 消失了"、"XX 走过就没了"：

  1. 屏幕上那个字符是从哪儿画上去的？
  2. 那个位置 bg[y][x] 里存的是什么？
  3. 如果 ① 和 ② 不一样，就是显示层/数据层不同步

看到"XX 变成别的字符了"：

  → 大概率是擦除逻辑用错误的 bg 值恢复了

看到"XX 位置该有的字符没有"：

  → 大概率是 .txt 里那个位置是空格，代码没画


============================================================
【八、教训】
============================================================

一开始我以为是"画图问题"—— 反复改 hall.txt 的字符位置，
甚至试图往 load_secene 加"D 也要跳过"的分支。全错。

真正的问题是"我把字符画到了屏幕上，但没告诉 bg[][]"。

调试这类 bug 的正确顺序：

  ① 先想清楚 bg[][] 数组是数据层，屏幕是显示层
  ② 分别检查：
     - 屏幕上想要显示的每个字符，是谁画的？
     - 那个位置 bg[][] 里存的是啥？
  ③ 如果两层不一致 → 立即找到 bug

不要在"改画面 vs 改代码"之间来回猜。先想清楚数据流。
