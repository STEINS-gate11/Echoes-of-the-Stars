============================================================
《星空回响》学习笔记 10 · 为什么用 WriteConsoleW 而不是 printf
============================================================

【学习时间】2026-07-22

【本笔记内容】
- printf 显示中文为什么不稳定
- Windows 控制台内部使用什么编码
- WriteConsoleW 为什么稳定
- 从 printf 一步步推导到 WriteConsoleW 的思考顺序
- 为什么打字机自然应该用 WriteConsoleW


============================================================
【一、你为什么会想到用 Windows 官方函数】
============================================================

不是凭空想到。你是被 printf 的问题一步步推过去的。

正常的思考顺序：

  1. 最先想到的是 printf，因为它是 C 教材第一章的函数。
  2. 直接 printf("你拿起那颗星星。") 有时正常，有时乱码。
  3. 你会先试常见修法（改代码页、加 /utf-8）。
  4. 但发现只要换电脑、换终端、换字体，行为就变。
  5. 于是查资料，发现 Windows 控制台内部编码是 UTF-16。
  6. Windows 提供一个直接写 UTF-16 的接口：WriteConsoleW。
  7. 它绕开 C 运行时和代码页，直连控制台，最稳定。
  8. 所以选它。

结论：

  用 WriteConsoleW 不是灵感，是"踩过 printf 的坑之后，找一条最短最稳的路"。


============================================================
【二、printf 为什么不稳】
============================================================

printf 是 C 标准库函数，它输出中文时依赖三层：

  1. 源代码文件的编码（UTF-8 / GBK）
  2. 编译器如何解释源代码里的字符串（/utf-8 等编译选项）
  3. 控制台使用的代码页（GBK / UTF-8 / UTF-16）

只要有一层不对齐，就会乱码。

而且：

  - Windows 控制台默认代码页是 GBK
  - VS 项目常用 UTF-8 源码
  - 玩家的机器上代码页可能又不一样
  - Emoji 在部分代码页里根本不支持


============================================================
【三、Windows 控制台内部编码】
============================================================

Windows 控制台的核心接口按 UTF-16 处理字符。

也就是说：

  - 无论 printf 用什么代码页
  - 最终 Windows 内部都要把它转成 UTF-16 才能显示
  - 中间的转换环节多，出错点多

而 UTF-16 就是 C/C++ 里的 wchar_t 类型使用的编码：

  wchar_t          Windows 上通常是 UTF-16
  L"中文"          就是一段 UTF-16 宽字符串


============================================================
【四、WriteConsoleW 为什么稳定】
============================================================

WriteConsoleW 的输入本来就是 wchar_t*：

  WriteConsoleW(handle, wchar_t*, length, ...);

它做的事情：

  1. 直接把 UTF-16 字符送进控制台
  2. 不经过 C 运行时缓冲
  3. 不受代码页影响

只要你构造出正确的 wchar_t 字符串，它就能显示对，不受这些影响：

  - 源码编码
  - 项目编译选项
  - 终端类型
  - 控制台代码页


============================================================
【五、这也就直接解决了打字机的第二个难题】
============================================================

如果你坚持用 char* + printf 做打字机：

  for (int i = 0; text[i] != '\0'; i++) {
      printf("%c", text[i]);
      Sleep(delayMs);
  }

问题：

  %c 每次只输出 1 个字节
  中文一个字在 UTF-8 里通常是 3 个字节
  拆开输出会乱码

你需要：

  1. 判断当前字节是中文的第几字节
  2. 一次输出完整的多字节字符
  3. 这一步涉及位运算和 UTF-8 编码规则

如果换用 wchar_t + WriteConsoleW：

  for (int i = 0; text[i] != L'\0'; i++) {
      WriteConsoleW(output, &text[i], 1, &written, NULL);
      Sleep(delayMs);
  }

因为：

  wchar_t 一个单位通常就是一个中文字符
  每轮输出 1 个 wchar_t = 打字机效果自然形成

所以选 wchar_t + WriteConsoleW 是同时解决"稳定显示"和"逐字动画"两个问题。


============================================================
【六、Emoji 引入的新问题】
============================================================

某些 Emoji 在 UTF-16 里由两个 wchar_t 表示（叫代理对）。

例如：

  🖼 (U+1F5BC) = 0xD83D 0xDDBC       两个 wchar_t

如果打字机每次只输出 1 个 wchar_t：

  第 1 次：0xD83D    → 乱码
  第 2 次：0xDDBC    → 乱码

于是又需要一种输出方式：

  一次把整段字符串交给 WriteConsoleW
  Windows 自己识别代理对，不拆开

这就是 printWideAll 存在的原因：

  void printWideAll(const wchar_t* text) {
      ...
      WriteConsoleW(output, text, len, &written, NULL);
  }

两个函数分工：

  delay_with_Chinese  正文（逐字动画，无 emoji）
  printWideAll        姓名栏（一次输出，允许 emoji）


============================================================
【七、思考顺序总结】
============================================================

  需求 1：显示中文
      → printf 有时对有时错
      → 查资料
      → 知道控制台内部是 UTF-16
      → 用 WriteConsoleW

  需求 2：中文逐字出现
      → printf + %c 按字节切
      → 中文多字节，处理复杂
      → wchar_t + WriteConsoleW 一次一个字，自然逐字

  需求 3：姓名栏要 emoji
      → 部分 emoji 是代理对
      → 每次输出 1 个 wchar_t 会拆开
      → 改成一次输出整段
      → 得到 printWideAll


============================================================
【八、一句话总结】
============================================================

  printf         最简单最兼容，但对中文/emoji不稳定
  WriteConsoleW  Windows 原生宽字符接口，直连控制台，最稳定

在这个项目里：

  - 稳定显示 → WriteConsoleW
  - 中文逐字 → 每次输出 1 个 wchar_t
  - Emoji 姓名栏 → 一次输出整段

三种需求都汇聚到同一个 Windows API 上。
