Bug 18 · C2078 报在数组声明行 · 第二维忘了算终止符
============================================================

【时间】2026-08-01
【严重程度】致命 · 编译不过
【位置】源.cpp 行 473 · mujian_sanwen 数组声明

============================================================
【现象】
============================================================

  扩写 mujian_sanwen 之后编译报：

    源.cpp(473): error C2078: 初始值设定项太多

  行 473 是数组声明行：

    const wchar_t* mujian_sanwen[7][24][9] = {

  奇怪的地方：错误报在声明行，不是报在某一页上。
  我第一反应是"某一页塞了超过 9 句"，往第三维方向查，查错了。

============================================================
【定位过程 · 走的弯路】
============================================================

  第一步（错）：以为是第三维超了
    数了每一页的句数，最多的两页是 8 句 + NULL = 9 个
    正好等于 [9]，没超

  第二步（错）：以为是某一页写超了没数出来
    写脚本逐页数 L" 的个数，报告最多 9 个
    还是没找到超的

  第三步（对）：数每一块有多少页
    脚本按 ^\t\{ 匹配章节块开头，按 ^\t\t\{ 匹配页开头

    结果：
      第 1 块（序幕）  页数 = 24   NULL终止在行 591
      第 2 块（第一章）页数 = 14
      第 3~7 块        页数 = 12

    序幕 24 页 + 1 个 { NULL } 终止符 = 25 个元素
    第二维只有 [24] → 溢出

============================================================
【根本原因】
============================================================

  数组的第二维要装：正文页数 + 1 个终止符

    mujian_sanwen[7][24][9]
                     ↑
                     这里必须 >= 最长章节的页数 + 1

  序幕有 24 页正文，加上 { NULL } 就是 25 个初始值。

  我扩容时的思路是"序幕 24 页 → 第二维开 24"，
  完全忘了 { NULL } 本身也占一个槽位。

  原来的代码是对的：
    [7][10][8]，序幕 8 页 + { NULL } = 9 个，第二维 10 有 1 格余量
  我扩容的时候把那格余量吃掉了。

============================================================
【为什么 C2078 报在声明行】
============================================================

  这是这个 bug 最容易误导人的地方。

  如果是第三维超了（某一页句子太多），编译器会报在那一页的行号上：
    源.cpp(995): error C2078

  如果是第二维超了（某一块页数太多），编译器报在声明行：
    源.cpp(473): error C2078

  因为第二维的边界是由声明决定的，编译器发现"这一块的元素比声明的多"，
  归咎于声明本身。

  ★ 记住这个规律：
    C2078 报在数据行  → 查那一行所在的最内层维度
    C2078 报在声明行  → 查外层维度（每一块有多少个元素）

============================================================
【修复】
============================================================

  第二维 24 → 25：

    const wchar_t* mujian_sanwen[7][25][9] = {

  外层循环也要跟上（play_the_pangbai 里）：

    for (int i = 0; i < 25; i++) {
        if (mujian_sanwen[idx][i][0] == NULL)break;

  内层 j < 9 不用改 —— 每页最多 8 句 + NULL = 9 个，刚好。

============================================================
【三处必须同时改】
============================================================

  这次扩容一共动了三个数字，少改一个就出问题：

  ┌────────────────────────┬─────────┬─────────┐
  │ 位置                   │ 原来    │ 改成    │
  ├────────────────────────┼─────────┼─────────┤
  │ 数组第二维             │ 10      │ 25      │
  │ 数组第三维             │ 8       │ 9       │
  │ play_the_pangbai 外循环│ i < 10  │ i < 25  │
  │ play_the_pangbai 内循环│ j < 8   │ j < 9   │
  └────────────────────────┴─────────┴─────────┘

  只改数组不改循环 → 第 11 页起永远不播（循环提前结束）
  只改循环不改数组 → 越界读内存，随机崩
  第三维忘了改      → 那两页 8 句的报 C2078
  第二维忘了 +1     → 序幕报 C2078（就是这次的 bug）

============================================================
【教训】
============================================================

  1. NULL 终止符占一个槽位
     字符串数组用 NULL 结尾时，
     声明的维度 = 实际内容数 + 1
     这个 +1 很容易在扩容时被吃掉

  2. C2078 的行号告诉你查哪一维
     报在声明行 → 外层维度
     报在数据行 → 内层维度
     我这次先猜内层，绕了两步

  3. 扩容多维数组要列表核对
     不要靠脑子记"改了几处"
     写下来：数组几维 + 几个循环，逐个打勾

  4. 原代码留的余量是有意义的
     [10] 装 9 个，看起来浪费一格
     那一格就是防这次这种错的
     扩容时不要把余量精确吃掉，留一格
