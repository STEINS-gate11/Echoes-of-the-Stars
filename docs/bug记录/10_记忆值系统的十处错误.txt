《星空回响》Bug 记录 10 · 记忆值系统的十处错误
============================================================

【发生时间】2026-07-29
【场景】首次实现记忆值系统 + 暂停栈,一次性写了约 60 行代码,
        代码审查发现 10 处错误。3 处编译不过,7 处逻辑错误。


============================================================
【背景】
============================================================

记忆值系统的设计:
  · 全局变量:memory_zhi(记忆值),memory_last(上次扣减时刻),
             memory_time(扣减周期 8000ms)
  · 暂停栈:time_zone[15] 数组,time_top 栈顶指针
  · 6 个函数:memory_clorur / draw_memory_secene / create_time /
             push_stack_time / pop_stack_time / now_time
  · 在 play_pangpai / play_the_pangbai / playconversation /
    begin_conver_history 四个函数里 push/pop
  · 主循环用 _kbhit + Sleep(50) 轮询,每 50ms 调 now_time()

代码是一次性写完的,写完后代码审查发现 10 处错误。


============================================================
【错误 ① · 变量定义在使用之后 · 编译错】
============================================================

▌ 现象
    int memory_clorur(int x) { ... }
    void draw_memory_secene() {
        setColor(memory_clorur(memory_zhi));    // ← 用了 memory_zhi
        ...
    }
    int memory_zhi = 100;                       // ← 定义在这里,晚了

▌ 原因
    C 是单遍编译。draw_memory_secene 用 memory_zhi 时,
    memory_zhi 还没被定义,编译器不认识。

▌ 修法
    把所有全局变量声明挪到函数定义之前:
        int memory_zhi = 100;      // ← 数据在前
        DWORD memory_time = 8000;
        DWORD memory_last = 0;
        DWORD time_zone[15];
        int time_top = 0;

        int memory_clorur(int x) { ... }   // ← 函数在后
        void draw_memory_secene() { ... }
        ...

▌ 教训
    数据在前,函数在后。这个规则和 bug 07 一脉相承。
    项目里 chaptercolors、the_chapter_Walls、mujian_sanwen
    都是这么组织的,新加代码要沿用这个约定。


============================================================
【错误 ② · 变量名拼错 · 编译错】
============================================================

▌ 现象
    void push_stack_time() {
        if (time_top < 15) {
            time_zone[top] = GetTickCount();  // ← top 不存在
        }
        ...
    }

▌ 原因
    真正的变量名是 time_top,写代码时手滑写成 top,编译器报
    "未定义标识符 'top'"。

▌ 修法
    time_zone[top]  →  time_zone[time_top]

▌ 教训
    变量命名带前缀(time_top 而不是 top)是好习惯 ——
    但前缀必须一致到底,一处漏掉整个函数就编不过。
    编译器会保护你,但错误信息很直白。


============================================================
【错误 ③ · 变量名拼错 · 编译错】
============================================================

▌ 现象
    int now_time() {
        ...
        if (memory == 0) return -1;    // ← memory 不存在
        ...
    }

▌ 原因
    真正的变量名是 memory_zhi,写代码时脑子里想的是
    "memory 归零",手上就写了 memory。

▌ 修法
    if (memory == 0)  →  if (memory_zhi == 0)

▌ 教训
    同一函数里前面刚写过 memory_zhi--,最后一行写成 memory,
    典型的思维定式失误。写完一段先编译一次,不要一口气写完。


============================================================
【错误 ④ · 初始化值错 · 一开始就触发结局 C】
============================================================

▌ 现象
    void create_time() {
        memory_last = GetTickCount();
        time_top = 0;
        memory_zhi = 0;           // ← 应该是 100!
    }

▌ 原因
    写代码时脑子想的是"归零",手写了 0。

▌ 后果
    游戏启动 → main 调 create_time → memory_zhi = 0
    → 立刻满足 "if (memory_zhi <= 0)" → 触发结局 C
    玩家看不到任何主界面之外的东西,游戏还没开始就结束了。

▌ 修法
    memory_zhi = 0  →  memory_zhi = 100

▌ 教训
    "初始化"和"归零"是两个概念,不能混用同一个数字 0。
    容易出这种错的地方:
      · 血量/记忆值初始化(应该满值)
      · 敌人 HP 初始化(应该满值)
      · 计数器归零(才应该 0)


============================================================
【错误 ⑤ · 栈的 top++ 位置错 · 越界风险】
============================================================

▌ 现象
    void push_stack_time() {
        if (time_top < 15) {
            time_zone[time_top] = GetTickCount();
        }
        time_top++;                  // ← 在 if 外面!
    }

▌ 原因
    push 应该"写数据 + 顶指针 +1"是一个整体操作。
    但把 time_top++ 写在 if 外面,导致栈满(top == 15)时:
      · if 里不写数据(正确)
      · 但 top 还是 +1(错误,变成 16)
    再 push 一次 → top = 17,越界地址访问,程序可能崩溃。

▌ 修法
    void push_stack_time() {
        if (time_top < 15) {
            time_zone[time_top] = GetTickCount();
            time_top++;              // ← 挪到 if 内,和写数据绑一起
        }
    }

▌ 教训
    "push 数据 + 顶指针递增" 必须一起做,一起失败或一起成功。
    这就是"原子操作"的概念 —— 半做半不做就是 bug。


============================================================
【错误 ⑥ · pop 下标混淆(其实对了,但不清晰)】
============================================================

▌ 现象
    void pop_stack_time() {
        if (time_top <= 0) return;
        time_top--;                                  // ← 先减
        if (time_top == 0) {
            DWORD temp = GetTickCount() - time_zone[time_top]; // ← 用 time_top
            ...
        }
    }

▌ 分析
    pop 之后 time_top = 0,time_zone[time_top] = time_zone[0]。
    功能上其实是对的。但代码读起来容易困惑:
      "time_top 变了,现在下标到底是几?"

▌ 修法
    DWORD temp = GetTickCount() - time_zone[time_top];
              → GetTickCount() - time_zone[0];

    直接写 time_zone[0],意图明确:
    "最外层暂停时刻永远在数组第 0 位"

▌ 教训
    能用常量下标就不用变量下标。可读性 > 灵活性。
    尤其是关键系统的核心逻辑,读起来越直白越好。


============================================================
【错误 ⑦ · 判断反了 · 最严重 · 记忆值永远不流失】
============================================================

▌ 现象
    int now_time() {
        int flag = 0;
        if (memory_zhi <= 0) return 0;
        if (time_top == 0) return 0;         // ← 反了!!!
        ...
    }

▌ 原因
    暂停栈的语义:
      · 栈非空(time_top > 0) = 有 push 未 pop = 暂停中
      · 栈空(time_top == 0) = 所有暂停都退出了 = 该扣值

    我写的是 "time_top == 0 就 return" —— 恰好反了。
    等于说:"栈空就不扣,栈非空才扣" —— 完全颠倒。

▌ 后果
    游戏运行时:
      · 主循环里栈永远是空的(0)
      · 每次进 now_time,直接 return 0
      · memory_zhi 永远是 100
      · 记忆值系统完全失效

▌ 修法
    if (time_top == 0) return 0;   →   if (time_top > 0) return 0;

▌ 教训
    暂停栈的 push/pop 逻辑一定要在纸上画一遍:
      · push 时栈从空到非空 → 从"计时中"进入"暂停中"
      · pop 时栈从非空到空 → 从"暂停中"回到"计时中"
      · 所以 "栈非空 = 暂停中 = 不扣值"

    写这类反义判断时,大声念一遍:
      "如果……那么……"
    "如果栈非空,那么不扣" —— 对
    "如果栈空,那么不扣" —— 错

    这是全篇最严重的 bug,不修的话整个系统作废。


============================================================
【错误 ⑧⑨⑩ · 提前返回没 pop · 栈永远不空】
============================================================

▌ 现象(以 play_pangpai 为例)
    void play_pangpai(int chapter) {
        push_stack_time();                           // ← push
        if (chapter < 1 || chapter>6) return;        // ← 直接 return,没 pop
        ...
        pop_stack_time();                            // ← 正常结束的 pop
    }

▌ 原因
    push 和 pop 必须严格配对。一次 push 必须对应一次 pop。
    如果函数在中间提前 return,push 已经发生,pop 没执行 ——
    栈里多出一个元素,永远没人来弹。

▌ 后果
    栈永远不空 → time_top 永远 > 0 → now_time 永远返回 0
    → 记忆值永远不扣 → 系统作废(和错误⑦一样)

▌ 修法(三处相似)
    play_pangpai:
        if (chapter < 1 || chapter>6) { pop_stack_time(); return; }

    play_the_pangbai:
        if (idx < 0 || idx > 6) { pop_stack_time(); return; }
        if (pangbai_alredy[idx] == 1) { pop_stack_time(); return; }

    begin_conver_history:
        if (!tail) {
            ...原来的代码...
            pop_stack_time();
            return;
        }

▌ 教训
    push/pop 就像 new/delete、fopen/fclose、malloc/free ——
    必须在函数的所有出口都成对出现。

    发现的方法:
      看着函数,数一下 push 和 pop 各出现几次。
      如果 push 出现 1 次,pop 应该也是 1 次。
      如果函数有 3 个 return,每个 return 前都要有对应的 pop。

    更好的做法(以后学到):
      C++ 里有 RAII 模式,把 push 放进构造函数,
      pop 放进析构函数,自动配对,不会漏。
      C 里可以用 goto 集中清理,或封装成宏。
      本项目为了简单,老老实实每个 return 加 pop。


============================================================
【总结:错误分类】
============================================================

按严重程度分类:
  · 编译错(3 处):①变量前后颠倒 ②top 拼错 ③memory 拼错
  · 逻辑反(1 处):⑦ 栈空/非空判断反了
  · 初值错(1 处):④ memory_zhi 初始化成 0
  · push/pop 不平衡(4 处):⑤ + ⑧⑨⑩
  · 可读性(1 处):⑥ 用变量下标不如用常量

按出错原因分类:
  · 命名一致性(②③):变量名拼错
  · 顺序意识(①):C 语言的先定义后使用
  · 语义思考(④⑦):"初始化 vs 归零"、"暂停 vs 计时"
  · 边界处理(⑤⑧⑨⑩):栈满、提前返回、多分支返回


============================================================
【复盘:为什么一次性写就错这么多】
============================================================

▌ 教训 1:模块太大,一次性写完就是找 bug
    这次的记忆值系统 60 行,涉及 5 个函数、5 个全局、1 个栈
    结构。一口气写完再回头找错,不如分块写:
      · 先写变量声明 → 编译 → 通过
      · 再写 draw_memory_secene → 编译 → 通过
      · 再写 create/push/pop → 编译 → 通过
      · 再写 now_time → 编译 → 通过
      · 最后集成到主循环

    每一步"编译通过"就是一次小胜利,错误也无处可藏。

▌ 教训 2:关键逻辑要在纸上画一遍
    暂停栈的 "push = 暂停,pop = 恢复,栈非空 = 暂停中" ——
    这三条逻辑在脑子里"应该很清楚",但真写代码时错误 ⑦
    还是发生了。原因是脑子记的是概念,手写时是符号,
    符号和概念之间有一步"翻译",这一步就出错。

    在纸上画状态图或状态表,写代码时对着看:
      time_top    含义      now_time 行为
      ---------   --------  -------------
      0           计时中    扣值(可以返回 1 或 -1)
      1..15       暂停中    不扣(必然返回 0)

▌ 教训 3:代码审查是必须的
    如果这段代码没审查直接跑,会看到:
      · 编译错(错误①②③)→ 立刻发现
      · 编译过后:游戏启动一瞬间进结局 C(错误④)→ 立刻发现
      · 修完 ④ 后:记忆值永远不掉(错误⑦)→ 5 分钟才发现
      · 幕间/对话时如果有嵌套 bug(错误⑧⑨⑩)→ 很难发现

    审查花 10 分钟,可以省掉 1~2 小时的调试时间。
    尤其是系统代码,写完先审查再跑。
